A Markdown File Sharing Network Across Agents and Chats: LangChain MCP, OAuth and AWS

Architecture and Python examples for a Markdown sharing network using LangChain MCP adapters, OAuth and AWS.

markdown-file-sharing-network-across-agentsmarkdown-mcp-service

1. Problem definition

When using Codex, ChatGPT web chats and other agents, useful explanations and working solutions stay in separate conversations. Moving that knowledge between tools usually means copying text or downloading files manually.

This project builds a shared Markdown document network that bridges those tools. An assistant saves selected content through MCP, and the document service stores it in a central AWS collection for later access. Filenames and project context help keep the documents organized.

The current MCP tool supports saving. Browsing and reopening documents happen through the document interface; agent-side search and retrieval would need additional tools.

2. Architecture: from the AI client to AWS storage

There are two views of the system. The first shows how the clients, authentication and storage fit together. The second follows one authenticated saving request through the Python service.

2.1 High-level architecture

AI clients send selected Markdown through the authenticated MCP service, while Cognito handles private sign-in. The service runs on ECS and writes directly to S3 and DynamoDB using its task role; the separate document API supports access to the shared collection.

2.2 Inside an authenticated saving request

The host calls save_markdown with its OAuth bearer token, and the service checks the session, user, write scope and document limits before dispatching the tool. Shared storage code writes the Markdown to S3, then publishes a READY record in DynamoDB. The result confirms each file separately; incomplete or uncertain writes must be reconciled before retrying.

Streamable HTTP describes the MCP transport

This implementation sends bounded Markdown content in a tool request. It does not continuously stream a conversation or perform multipart file streaming into S3. The source limits each file to 256 KiB, each batch to ten files and total content to 2 MB.

3. Technology overview

  1. MCP connects the clients to the saving operation. Codex and ChatGPT use their MCP connections to call save_markdown with complete Markdown and its document context.
  2. LangChain’s MCP adapter connects the agents. This design uses langchain.mcp.MCPAdapter to load document tools into a LangChain agent. The agent runs in a Docker container on ECS and calls the shared document endpoint.
  3. Docker and ECS host the workloads. The LangChain agent and the document service use separate containers. The agent uses the MCP adapter as its client; FastAPI/FastMCP exposes the saving tool on the service side. CloudFront provides the public HTTPS endpoint.
  4. OAuth and Cognito control access. The host connects through the service’s OAuth adapter and the user completes Cognito email OTP privately. The service checks identity and write permission before calling storage.
  5. S3 and DynamoDB organize the collection. S3 stores Markdown content. DynamoDB holds the document lookup record and any linked work item.

The adapter turns remote MCP operations into tools the agent can call. OAuth supplies the authorized connection, while the model provider supplies the agent’s reasoning. See LangChain’s MCP adapter documentation.

All CloudFront addresses below use the five-character placeholder a7k2q. Replace it with the configured distribution hostname; these are documentation examples.

4. The Python tool and document contract

The design has two Python roles: a LangChain agent that uses the MCP adapter, and a document service that exposes the saving tool. The client handles model-provider integration and tool calls; the service handles authorization, validation and storage.

4.1 Register the tool

This excerpt shows the tool and transport setup. The real application mounts it at /mcp, starts its lifespan manager, installs authentication and request-limit middleware, and registers OAuth discovery and adapter routes. This excerpt is not a standalone authenticated server.

"""Register the saving tool inside the existing authenticated MCP application."""

from fastmcp import FastMCP

from mcp_services.storage_service import save_batch
from mcp_services.validation_service import UploadBatch


def build_mcp_app(config: dict):
    """Build the transport mounted behind the application's OAuth ingress."""
    mcp = FastMCP("Markdown Documents", mask_error_details=True)

    @mcp.tool()
    async def save_markdown(payload: UploadBatch) -> dict:
        """Save validated files and return their confirmed storage outcomes."""
        return await save_batch(payload, config)

    return mcp.http_app(
        path="/",
        stateless_http=True,
        json_response=True,
        host_origin_protection=True,
        allowed_hosts=[
            config["PUBLIC_BASE_URL"].removeprefix("https://"),
            config["MCP_ORIGIN_HOST"],
        ],
        allowed_origins=[config["PUBLIC_BASE_URL"]],
    )

4.2 Validate once, then call shared storage

The storage adapter checks the complete batch before writing. The shared writer stores the latest Markdown bytes in S3 and publishes successful records as READY in DynamoDB. Each file has its own outcome; the batch is not an atomic transaction.

"""Bridge the asynchronous MCP handler to the shared storage operation."""

import asyncio

from botocore.exceptions import BotoCoreError, ClientError

from mcp_services.storage_service import write_documents
from mcp_services.validation_service import UploadBatch, prepare_payload


async def save_batch(payload: UploadBatch, config: dict) -> dict:
    """Return success only when all requested files reach READY."""
    prepared = prepare_payload(payload)
    try:
        results = await asyncio.to_thread(write_documents, prepared, config)
    except (BotoCoreError, ClientError):
        raise ValueError("Storage not confirmed; reconcile before retrying") from None

    return {
        "success": all(item["status"] == "READY" for item in results),
        "files": results,
    }

write_documents creates Boto3 clients with task-role credentials and bounded timeouts, calls the shared store_documents function, and closes the clients. Automatic AWS write retries are disabled here because an uncertain write needs reconciliation.

4.3 Send document content as tool arguments

The payload wrapper below is the MCP tool’s argument object. The personal service supplies its fixed username default and separately verifies the caller. A general-purpose multi-user service would need its own identity-to-collection rules.

{
  "payload": {
    "file-group": "learning-chatgpt",
    "files": [
      {
        "name": "cognito-authentication.md",
        "content": "# Cognito authentication\n\nThe complete explanation.\n",
        "metadata": {
          "project": "chatgpt-web-chat",
          "relative_path": ""
        }
      }
    ]
  }
}

For Codex notes, use the appropriate project and file group. relative_path is descriptive metadata in this implementation; it does not change the S3 object key. The storage layout is agent-work/raw-markdown/<user>/<file-group>/<filename>.

The current tool receipt returns the file ID, status and storage key for confirmed files. It does not promise an immutable S3 version or return a version ID or content hash; the assistant must not invent those values.

4.4 LangChain MCP adapter and model provider

The adapter loads the document tool and makes it available to a LangChain agent. Pass the configured provider/model identifier as model, install the matching LangChain provider package, and configure its credentials through the runtime’s secret configuration. Keep the adapter context open until the agent finishes.

"""Connect a model-backed LangChain agent to the document MCP tool."""

from fastmcp import Client
from langchain.agents import create_agent
from langchain.mcp import MCPAdapter


async def run_document_agent(model: str, request: str) -> dict:
    """Run a saving request with tools available for the full agent call."""
    client = Client("https://a7k2q.cloudfront.net/mcp/", auth="oauth")

    async with MCPAdapter(client) as adapter:
        tools = await adapter.list_tools()
        agent = create_agent(
            model=model,
            tools=tools,
            system_prompt=(
                "Save only the Markdown content requested by the user. "
                "Preserve its complete text, filename and project context. "
                "Report success only for files with READY status. "
                "Do not retry an uncertain write automatically."
            ),
        )
        return await agent.ainvoke(
            {"messages": [{"role": "user", "content": request}]}
        )

The host’s OAuth session authorizes the MCP call. Model-provider credentials are separate and are never sent in the document payload. The example hostname is a placeholder.

5. The saving skill used by the assistant

The skill is a short set of instructions for selecting content, preparing the payload and interpreting the result. It contains no credentials and does not run a background upload process.

For Codex, place this in .agents/skills/save-learning-document/SKILL.md within the project. For a ChatGPT plugin, bundle it under skills/save-learning-document/SKILL.md. The connected MCP server provides the actual operation. See the official skill packaging guide.

---
name: save-learning-document
description: Save a selected explanation or local Markdown file to the connected document collection when requested.
---
1. Keep the complete requested content; do not silently summarize it.
2. Choose a safe .md filename and the correct project and file group.
3. Discover the connected save_markdown tool and follow its current schema.
4. Send the document in the payload argument. Do not request passwords or tokens.
5. Confirm success only when each requested file returns status READY.
6. Report file_id and the saved name. If storage is uncertain, preserve the
   content and reconcile the file_id before retrying.

Use a project-specific file group such as learning-codex or learning-chatgpt, and set the document’s project deliberately. The server’s verified identity controls access; changing metadata cannot grant access to another collection.

6. Connect ChatGPT with a plugin

The plugin packages the MCP endpoint and optional saving skill. Python runs in ECS; there is no Python script to install inside the ChatGPT conversation.

  1. Describe the plugin. A root plugin.json identifies the package.
  2. Declare the server. A root mcp.json points to the HTTPS endpoint and selects OAuth with DCR.
  3. Bundle the saving skill. Include the skill folder from the saving-skill section.
  4. Connect and sign in. Install or connect the private plugin through the host’s supported flow, complete Cognito login privately and verify that save_markdown appears before using it.

The connection uses OAuth without OIDC scopes because this adapter advertises the write permission rather than an OpenID identity service. Package metadata does not contain a client secret. These examples follow the current plugin packaging format; host access and supported connection options must be checked in the target account.

7. Connect Codex to the same MCP endpoint

Codex can connect directly to the remote MCP server. Add the endpoint, start OAuth login and then check the active server’s tools.

codex mcp add gb-markdown --url https://a7k2q.cloudfront.net/mcp/
codex mcp login gb-markdown --scopes markdown-api/write
codex mcp list

The equivalent server settings belong in the active Codex configuration:

[mcp_servers.gb-markdown]
url = "https://a7k2q.cloudfront.net/mcp/"
scopes = ["markdown-api/write"]

Use either the add command or the configuration entry to register the server, then complete login. In the Codex terminal interface, /mcp shows active servers. Check that the client’s actual callback is accepted by the adapter; registration alone does not prove a working session. See Codex MCP configuration and OAuth.

With the skill available, Codex can read a selected local Markdown file and pass its contents to the same saving tool. No second Python uploader is required for this route.

8. DynamoDB table schema

The updated document index uses username as its string partition key and file_id as its string sort key. The UserFiles table declares no secondary index. Path-based uploads retain the same document ID when the same owner updates the same canonical path.

  DeletionPolicy: Retain
  UpdateReplacePolicy: Retain
  Properties:
    TableName: softrobots-document-api-user-files

    AttributeDefinitions:
      - AttributeName: username
        AttributeType: S
      - AttributeName: file_id

    KeySchema:

{
  "username": "example-user",
  "file_id": "path-derived-document-id",
  "s3_path": "s3://example-document-bucket/agent-work/raw-markdown/example-user/learning/cognito.md",
  "file-group": "knowledge",
  "created_at": "2026-10-30T14:00:00+00:00",
  "status": "READY"
}

Only the key attributes belong in CloudFormation’s AttributeDefinitions. The other fields are item attributes. The compact record removes the old metadata map, content hash, separate bucket/key fields and S3 version ID. Existing records remain readable and become compact on a successful update.

The path-based writer stores the latest bytes and uses S3 ETag conditions to reject conflicting writes. Source binding stays in S3 object metadata. It does not promise an atomic S3/DynamoDB transaction or automatic recovery after an uncertain result.

Integration status: this schema comes from the other agent’s latest compact-storage implementation. Its task record reports local verification with deployment blocked. The MCP service’s vendored storage modules still use the earlier versioned/PENDING flow shown above; they must be updated before claiming this compact schema is used end to end.

9. Package the service with Docker and deploy to ECS

Build a separate Docker image for the LangChain agent and for the document service. The delivery flow is the same for each workload: build and verify the image, publish it to Amazon ECR, then update ECS using the exact image digest.

  1. Build the Docker image. CI installs locked dependencies and copies the service modules into the image. The process runs as a non-root user.
  2. Verify the image. CI runs the source tests and checks imports and the container user. It exports the tested image for the deployment job.
  3. Push to ECR. The deployment job uses GitHub OIDC to assume its AWS role, tags the tested image with a unique release identifier and pushes it to ECR.
  4. Update ECS by digest. ECS receives the exact image reference. The task execution role permits image retrieval; the application’s task role permits its scoped AWS storage operations.
  5. Run the container. ECS pulls the image and starts Uvicorn on port 8000. The service’s configured origin and CloudFront route requests to the running task.
  6. Verify the release. Check deployment completion and the changed public boundary. Authenticated login, saving and retrieval remain separate acceptance checks.
FROM python:3.12-slim@sha256:aa943ce411423c7582288f18707ff66eddcbaeb510502d747a72aeb34f30d159
WORKDIR /app
COPY requirements.txt ./requirements.txt
RUN pip install --no-cache-dir -r requirements.txt && useradd --uid 10001 --create-home appuser
COPY services/ /app/services/
COPY mcp_services/ /app/mcp_services/
COPY app.py /app/app.py
USER 10001
EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log", "--no-proxy-headers", "--limit-concurrency", "32"]

The Dockerfile above shows the document-service image. The LangChain agent image includes langchain[mcp], its model-provider package and the agent entry point. Run that image as a separate ECS workload with its own configuration and credentials.
