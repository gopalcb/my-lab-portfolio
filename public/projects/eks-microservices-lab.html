SYSTEM DESIGN / EKS MICROSERVICES LAB

From an authenticated browser request to a committed registration, its HTTP response and the workers that finish the event—across AWS, Kubernetes and Linux boundaries.

TARGET ARCHITECTURE · DOCUMENTATION ONLY

The project currently contains plans and learning guides. Application code, Terraform, charts and deployed EKS resources do not exist yet. Pods, containers, placements and numbered paths below describe the system to be built, not running infrastructure.

What is being built

EventHub is a tenant-aware event-registration platform. A user signs in, reads an event, and reserves a seat. The application must reject another tenant’s data, prevent two requests from selling the last seat twice, and produce independent notification and audit outcomes even when processes restart. Those business rules are the reason for the Kubernetes, networking and recovery work.

The target combines TypeScript/Node.js Fastify APIs and workers, one Python synthetic monitor, private EKS workers, RDS PostgreSQL, SNS/SQS and S3. Terraform, ECR, Helm and Argo CD supply infrastructure and delivery. NGINX Gateway Fabric is the main edge target after the bounded F5 Ingress learning/migration exercise. Istio is a later security stage; it is not silently present in the baseline.

The AWS landscape: subnet to running container

Read the map from the client at the top into the customer VPC. A pod is the network boundary; its application container is the running process inside it. The three AZ columns illustrate the reference replica counts from the implementation resource map. They do not guarantee that a real scheduler will create exactly this placement or that a smaller learning environment has the same availability.

EKS cluster membership is a logical relationship rather than one box containing every AWS service. The managed control plane is separate from worker compute. NLB interfaces are public-facing while NGINX pods and application nodes stay private. RDS uses its own isolated data tier; ECR, SNS/SQS and S3 are regional services reached through the selected AWS connectivity paths.

A registration request, end to end

The concrete example below is a proposed API contract for implementation: POST /registrations, a bearer token from the selected Keycloak issuer, an idempotency key, and an event identifier. The application derives tenant scope from verified identity rather than trusting a body field. Region, public API/issuer hostnames, certificates and exact OpenAPI schemas still need to be selected and tested.

Step What actually happens What this proves / does not prove
0 · Obtain identity The browser uses the selected OIDC login flow. Keycloak issues the token. identity-service manages profiles and roles; it is not the authorization server. Issuer exposure, client settings and callback URLs are implementation gates. A token alone does not authorize another tenant’s event.
1 · Resolve and connect On a cache miss, the resolver obtains the API address via Route53/NLB DNS. The browser opens TCP 443 and negotiates TLS with NGINX through NLB forwarding. DNS is a lookup, not a request proxy. NAT is not this ingress path.
2 · Terminate and route A selected NGINX pod handles the public certificate, host/path and HTTPRoute. Its upstream connection targets an eligible registration endpoint. NLB target health, route acceptance and app readiness are distinct checks. Exact target port and endpoint selection come from rendered controller state.
3 · Reach the container The packet crosses the applicable VPC/node routing and veth boundary to the pod IP, then the registration container’s listener on 0.0.0.0:3000. VPC CNI supplies routable pod addresses. The Kubernetes API, Deployment and container runtime are not per-request HTTP proxies.
4 · Authorize and transact Registration verifies JWT signature/issuer/audience/expiry/scopes using trusted keys, then tenant/resource access. A bounded DB operation enforces capacity and idempotency and writes registration + outbox atomically. Cached JWKS normally avoids a synchronous profile-service lookup on every request. SQL checks, locks/conditional updates and uniqueness must survive real concurrency.
5 · Commit and create the response PostgreSQL returns commit success on the DB connection. The API constructs the registration result; the proposed new-registration response is 201 Created only after durable commit. A lost connection around commit can make the result uncertain. An idempotent retry must reconcile the original outcome rather than blindly sell another seat.
6 · Return to the user The upstream HTTP result returns to NGINX. NGINX sends the response over the client’s TLS connection through the matching NLB flow; the browser receives the status/body. The response is not a new outbound call through NAT. Its success does not mean the notification worker or audit worker has completed.
7 · Finish asynchronously The publisher sends committed outbox events to SNS. Notification and audit process their own SQS copies and record durable results. Queue completion needs its own evidence and latency measurement. It is separate from HTTP acceptance.

For a new registration, the draft response can report the registration identifier and confirmed reservation while describing subscriber delivery as pending. Replaying the same idempotency key with the same intent returns its original outcome; mismatched reuse must be rejected under the final API contract. A timeout after commit must not lead to duplicate business effects. No sample response here is captured runtime output.

Inside the worker: pod, container and network namespace

The registration container runs node dist/server.js; the outbox Deployment uses the same image digest with node dist/outbox-publisher.js. Kubelet and containerd create those processes from desired state. A node has one Linux kernel. Namespaces provide views and cgroups apply resource budgets; a pod is not a virtual machine with its own kernel.

A Service name and ClusterIP are stable discovery/routing abstractions while pods are replaced. EndpointSlice watches carry readiness and backend addresses to controllers and node agents. They do not forward packets themselves. A TCP connection can remain mapped to its selected backend; changing readiness does not instantaneously erase all established traffic.

Routes, security groups and return paths

Tier / boundary Planned EventHub behavior Check before accepting it
Public /24 tiers NLB entry and same-AZ NAT. Public route tables have an IGW default. Correct subnet discovery, target registration and health listeners; a public route does not make private workers public.
Workload /20 tiers Private EC2 and VPC pod addresses; local destinations stay local. Internet dependencies use the chosen SNAT/NAT design. Per-AZ address headroom, warm CNI allocation, replacements and rollout surge; exact source-IP behavior.
Data /24 tiers RDS subnet group; no Internet default; role-specific access to 5432. Client TLS verification, restrictive DB SG and response reachability. Multi-AZ is not a substitute for tested backup/restore.
EKS ENI /27 tiers Private cluster API communication, headroom for lifecycle operations. Separate administration connectivity; no claim of SSH access to managed EKS etcd hosts.
SG / NACL / NetworkPolicy Stateful SG rules, stateless subnet NACLs and enforced Kubernetes policy protect different boundaries. Test both request and return traffic, appropriate ephemeral ports, DNS TCP/UDP 53 and required control/telemetry paths.

Application pods do not automatically gain useful isolation merely by sharing the apps-dev namespace. Test default-deny and each required allow path against the chosen policy engine. NAT supports outbound Internet sessions; interface endpoints use their own SG/policy/private-DNS checks, and S3 gateway endpoints install a service-prefix route. These mechanisms solve different destination paths, not interchangeable versions of Service networking.

One database commit, two independent subscribers

The publisher and consumers need separate service accounts/IAM scopes: publication, receiving/deleting messages, and audit bucket writes are different permissions. Notification replicas compete for one queue’s work; audit receives its own copy. Visibility timeout, acknowledgement order, poison-message handling, DLQ repair and redrive all belong to the application’s correctness tests.

The reference illustration has 12 application pods: identity 3, registration 3, publisher 1, notification 2, audit 2 and monitor 1. These are sizing inputs from the resource map. Each Deployment’s rollout allowance, platform pods, node replacements and warm CNI addresses add demand. More replicas also multiply DB pools and downstream work; scaling must respect those budgets.

The dead-letter queues are eventhub-dev-notifications-dlq and eventhub-dev-audit-dlq. Their retention, redrive permissions and repair procedure must be configured and tested independently.

Add mesh trust as an explicit later cutover

The baseline is NLB → NGINX → application endpoint. The security stage adds a dedicated private Istio gateway. NGINX verifies the gateway’s server certificate CA and hostname; the gateway then connects to app workloads with mesh mTLS and the permitted principal. Browser TLS, backend server TLS and mesh authentication are separate connections and policies.

  • Verify probe and metric paths, JWT propagation, route parity and backend certificate renewal before STRICT mTLS.
  • Prove forbidden plaintext and wrong-principal traffic are rejected while the intended user path still succeeds.
  • Measure the extra proxy hop’s latency/resources, and document the cutover and recovery route instead of relaxing policy to make traffic pass.

What keeps the request path running

Kubelet reports pod status and manages containers; readiness controls eligible endpoints, while dependency-independent liveness avoids DB outage restart loops. During termination, endpoint propagation and HTTP draining overlap. Handle TERM, stop new work, drain bounded in-flight operations, close pools, and test duplicate-safe queue retry if the grace deadline is reached.

The initial baseline uses managed EC2 capacity. Stable system placement precedes later constrained Karpenter application pools; HPA or KEDA must have one scale owner per workload. Topology spreading, compatible rollout/PDB settings and correctly sized node capacity are needed before reference replicas can establish useful AZ fault tolerance.

Scenario Expected evidence
One successful registration Selected hostname/certificate; NLB→NGINX route; registration trace and committed DB result; correct 201 response; later notification + audit completion.
Last-seat race / retry after timeout No oversell, no duplicate registration, stable idempotent result and outbox consistency despite uncertain client receipt.
Same-node succeeds, cross-node fails Discovered placement, pod IP/ENI/routes, policy/SG/NACL and return-path comparison; do not blame DNS without evidence.
Pod restart / unavailable replica Readiness and endpoint changes, graceful termination, replacement image digest, bounded request behavior and successful original-flow retest.
Worker or AZ interruption Actual remaining capacity/placement, gateway health, DB profile and queue continuity; no claim of HA from replica count alone.
Publisher/consumer crash / data restore Outbox state, independent subscriptions, durable idempotency, DLQ/reconciliation and business-correct restored state.
Wrong tenant / AWS role / mesh peer Separate denied-path results for user authorization, IAM and network/mesh identity; successful encryption alone is insufficient.

Proposed reference targets remain 50 requests/second with a defined mix and burst, 99.9% monthly eligible-request availability, and recovery objectives RPO ≤15 minutes/RTO ≤60 minutes. None is measured. The project’s planned 30 drills and 12 incident reports must include the actual revision, deployment profile, signal path and restoration proof. Short test windows and static diagrams do not establish those outcomes.

Implementation still needs chosen account/region/domain, compatible versions, exact controller-generated resources and listener ports, finalized API schemas and measured node/endpoint placement. This article and the implementation walkthrough define a target to build and test; they do not report a live cluster.
