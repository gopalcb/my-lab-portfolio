SYSTEM DESIGN / CODEX MULTI-AGENT SYSTEMS

Codex Multi-Agent Collaboration gives bounded local workers a durable way to receive assignments and return results. One coordinator keeps responsibility for scope, integration and the final outcome. A remote Bedrock Agents bridge is a separate, proposed extension.

Collaboration starts with an explicit choice

The implemented project is a standalone local plugin, multi-agent@gb-multi-agent. Its lifecycle gate recognizes a leading /multi-agent followed by task text. Installation alone does not activate collaboration. Ordinary prompts follow the regular workflow; an ordinary follow-up closes a prior active collaboration scope.

Activation creates a scope and registers a root identity. Native children and externally supervised workers receive distinct identities with parent linkage. The hook supplies the assigned agent ID and client instructions. A request to collaborate is therefore separate from proof that registration succeeded.

The installation receipt records version 0.1.0 and a profile hook bridge. Project documentation describes that bridge as a compatibility measure for CLI 0.163.0, where bundled handlers were not exposed. Hook review and trust remain prerequisites. The receipt establishes installation metadata, not current service health or a successful collaboration session.

A durable inbox carries the work

The local stack combines an authenticated loopback HTTP API, Flask, SQLAlchemy and SQLite. Waitress binds to 127.0.0.1 on an allocated port. Singleton locks protect startup. Private runtime data lives outside source and plugin cache, so refreshing code does not replace collaboration history.

Identity, presence and events have separate responsibilities: system-agents identifies participants, communication tracks attachments and presence, and events stores assignments, claims and results. Recipients read their inbox, claim an assignment and persist completion or failure. Event ID reuse with identical content supports retry; conflicting content is rejected.

The durable inbox is the delivery contract. The optional native queue adapter is documented as best effort and unverified on the cited CLI version. Queue acceptance does not prove that an idle agent woke, claimed work or completed it. Explicit inbox handling keeps those stages observable.

Supervise execution and preserve uncertainty

A named launch_agent event targets the reserved system recipient. The dispatcher validates prompt, workspace and launch mode, limits each scope to three live external workers, and creates a private job receipt before starting execution. The working directory must resolve within the initiating workspace. This check constrains launch location; it is not a filesystem sandbox.

The supervisor observes scope and worker presence, heartbeats during execution and terminates an inactive worker. Service reconciliation handles owner death and stale leases; inactive scopes eventually allow service shutdown. Heartbeats demonstrate liveness without converting idle state into working state.

Recovery retains claimed launches whose external effects are uncertain rather than blindly replaying them. Coordinator review must reconcile outcomes before retry. Explicit file ownership, preservation of other workers' edits and controlled integration remain essential: messages and lease expiry cannot prevent every conflicting write.

Proposed extension: Bedrock Agents bridge

Status: design only. The aws-bedrock-agent-caller directory is empty in the inspected checkout. No remote adapter implementation or cloud execution is established. The proposal adds a custom tool or MCP bridge that sends only approved task inputs to an allowlisted Bedrock agent and alias.

Bedrock Agents InvokeAgent returns an event stream and can return control for configured actions. The proposed bridge must handle those outcomes explicitly; a remote response grants no local filesystem access. AgentCore InvokeAgentRuntime addresses a different runtime interface. Bedrock managed multi-agent collaboration uses an AWS supervisor with collaborator agents; that is another orchestration model, separate from this local coordinator and inbox design.

Implementation would need bounded retries, cancellation semantics, session isolation and explicit handling of uncertain remote effects. Those are proposed requirements. Current review confirms local source structure and the empty adapter directory; it does not establish live hook trust, worker execution, IAM readiness or remote success.
