SYSTEM DESIGN / BEDROCK AGENT INTEGRATION

A proposed InvokeAgent adapter with explicit destination approval, durable attempt mapping, bounded responses and honest handling of uncertain remote effects.

PROPOSED ADAPTER · NO CLOUD EXECUTION

The local codex-multi-agent plugin implements collaboration and supervised Codex workers. The aws-bedrock-agent-caller directory is empty. Bedrock integration remains a design proposal; this static document makes no service connection and supplies no deployed agent IDs.

Extend execution behind a narrow boundary

The proposed adapter would let the coordinator send one approved task to an existing Amazon Bedrock Agent and review its bounded result. It would use Bedrock Agents InvokeAgent, rather than AgentCore Runtime’s separate API. A common task contract could support native, CLI and remote execution while preserving their different failure models.

The existing dispatcher accepts only local launch_agent payloads containing prompt, workspace and mode. It has no Bedrock execution branch. Adding remote work therefore needs a reviewed contract and implementation, not a new mode string slipped into an existing launch request. The portfolio viewer remains a static reader; credentials and invocation belong in an authorized backend or local adapter.

Resolve identity and data before sending

Require an explicit expected account, named credential profile and region. Resolve credentials through approved local mechanisms; never put keys in assignments. An authorized run would verify caller identity before invocation. Identity verification establishes who is calling, while IAM and approved task scope determine what may be done.

Allowlist the exact agent ID and alias ID together with their account and region. Reject a mismatch instead of falling back to defaults or discovering another target. Alias routing can change, so record the reviewed destination and available version evidence per attempt. AWS scopes bedrock:InvokeAgent permission to an agent-alias resource; invocation rights need not grant agent creation or editing. AWS’s IAM examples describe that resource boundary.

Send only the problem statement, relevant approved excerpts, constraints and result schema. Exclude repository-wide context, credentials, native session histories and unrelated personal data. Enforce byte limits before serialization, cap requested work and set deadlines and cost/concurrency budgets. These proposed controls must be executable validation rules, with clear errors and tests, rather than instructions that the remote model may ignore.

Map local attempts to remote conversation state

Keep separate identifiers for the local task, local attempt and remote sessionId. Persist their association with destination, request digest and dispatch state before sending. Each independent task gets isolated conversation state. A deliberate continuation reuses its mapped session; a fresh attempt must explicitly decide whether prior context is intended. AWS documents that the same session ID continues a conversation. The InvokeAgent contract also defines endSession and response event types.

Proposed receipt, not current API payload:
local_task_id → local_attempt_id → remote_session_id
destination: expected_account / region / agent_id / alias_id
request_digest + send_state + observed_outcome
bounded_result + evidence + unresolved_effects

The consumer should treat the response as typed events, not assume one plain text body. Decode chunk bytes incrementally and preserve attribution separately. Apply limits to total bytes, event count and duration; classify trace, files, return-control requests and errors explicitly. Reject unsupported events safely. A partial answer or initial HTTP success cannot establish a complete result. Keep trace collection disabled by default and sanitize any approved diagnostics.

AWS supports optional final-response streaming, and documents additional streaming permission requirements. The adapter must handle both a single final chunk and streamed chunks without changing its result contract. The application invocation guide explains response streaming. Limits and stream interruption behavior still need implementation and focused tests.

Separate remote capability from local approval

Remote action groups can invoke Lambda functions or return requested actions to the caller. Their permissions and downstream effects are separate from the local coordinator’s file ownership rules. Review the agent service role, Lambda permissions and connected resources before any live task; invocation can cause effects beyond producing text. AWS describes these action-group execution choices.

For caller-side execution, treat returnControl as a proposed action requiring validation and authorization. Do not execute arbitrary returned commands. If an action is permitted and completed, its result must be associated with the returned invocation ID in the continuing session. AWS documents the return-control handoff. A text-only initial integration could reject action requests and report that limitation.

Record uncertainty when a connection fails after sending. Configure SDK retries deliberately and account for them in the attempt budget; a new session can still repeat a business effect. The API has no general client request token that turns this workflow into exactly-once execution. Require action-level idempotency and reconciliation before retrying effectful work. Ending a conversation is not a rollback of completed actions.

Before declaring the adapter ready, implement offline request validation, event fixtures, interruption and duplicate-attempt cases, then separately obtain authorization for a tightly scoped dev invocation. The coordinator must compare the returned evidence with the original acceptance criteria and report unresolved effects. This note verifies the proposal’s source boundary and AWS contract, while adapter behavior, IAM configuration and live execution remain unverified.
