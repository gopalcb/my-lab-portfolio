Terraform foundations and state

The EventHub learning environment owns its network, EKS, ECR, RDS and message resources. Bootstrap protected state separately.

The target design bootstraps a dedicated encrypted, versioned, access-restricted S3 state backend separately from disposable environments. State can contain sensitive values even if terminal output hides them. Compatible Terraform supports native S3 lockfiles through use_lockfile = true; concurrency and lock ownership need an actual test.

Application correctness first

Build identity-service and registration-service first, then registration-outbox-publisher, notification-service, audit-service and monitoring-agent-service.

TypeScript and Fastify are the proposed HTTP/worker stack. Validate environment and incoming JSON at runtime; compile-time types do not validate an HTTP body. Define contract schemas, tenant authorization, sanitized error classes and bounded HTTP/SQL/AWS timeouts. Registration concurrency tests need real PostgreSQL constraints/transactions, not only mocked repository calls.

Startup probes allow initialization; readiness decides whether this replica should accept traffic; liveness detects a condition worth restarting. An unavailable database should not create endless liveness restart storms. On SIGTERM, stop accepting work, drain bounded in-flight requests, finish or release queue work safely, close pools and exit within the pod grace period.

The small Python monitoring agent uses dedicated test tenants, scoped client credentials and bounded requests. A Deployment can run continuous checks; a CronJob needs explicit overlap and execution-deadline handling. It emits synthetic outcomes and telemetry, while node exporters and OTel collectors retain platform collection responsibilities. An outside probe is still required to observe total cluster failure independently.

Source, image, container and socket

ECR eventhub/registration-service supplies one digest to two Deployments: registration-service and registration-outbox-publisher.

A multi-stage Docker build keeps compilers and test tools out of the final image. Use selected, supported base images pinned to digests and a dependency lockfile. Install production dependencies without baking credentials into layers. A non-root runtime, exec-form entrypoint and minimal required files help, but image size is not artifact provenance. 

# Proposed services/registration/Dockerfile.
# CI must supply approved digest-pinned Node builder/runtime references.
ARG BUILD_IMAGE
ARG RUNTIME_IMAGE

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
RUN npm prune --omit=dev

FROM ${RUNTIME_IMAGE} AS runtime
WORKDIR /app
COPY --from=build --chown=10001:10001 /app/dist ./dist
COPY --from=build --chown=10001:10001 /app/node_modules ./node_modules
COPY --from=build --chown=10001:10001 /app/package.json ./package.json
USER 10001:10001
EXPOSE 3000
CMD ["node", "dist/server.js"]
# Publisher Deployment overrides command with:
# ["node", "dist/outbox-publisher.js"]

Build once, promote the digest

The registration image is tested once and promoted through environment values; the publisher reuses that same artifact.

GitHub Actions OIDC exchanges a workflow token for short-lived AWS credentials. Restrict the role’s audience and subject to the intended repository and branch or protected environment; prove an unauthorized subject fails. Use minimum workflow permissions and reviewed/pinned action dependencies. Avoid static AWS keys in CI.

The proposed pipeline layers lint/typecheck, unit/contract tests, PostgreSQL integration/race tests, image build, image/IaC/chart scans, SBOM, provenance and signatures/attestations. Admission then verifies the selected deployment trust policy. An authorized publisher can still publish an unsafe artifact; ECR scanning alone is not a software-supply-chain policy. Findings require exploitability review and expiring exceptions.

  • Use immutable tags to reduce replacement mistakes and digests to identify exact content. Promote the same digest across environments.
  • Record the source revision, builder identity, target architecture and verification policy.
  • Test a replacement node’s cold image pull: ECR/DKR/S3 reachability and node permissions must work. Application Pod Identity does not authorize kubelet image pulls.

Migrations and rollback

The registration migration Job changes the registration schema under one owner; API and publisher versions must remain compatible.

Choose one migration Job owner and explicit retry/concurrency rules. A Job is not automatically safe to rerun after partial failure. Expand/contract lets old/new application versions coexist, bounds lock/query impact and defers destructive contraction until old readers are gone. Validate backfill counts and constraints; do not infer success from Job completion alone.

Revert the application digest through Git only if its schema and event contracts remain compatible. Otherwise choose the reviewed forward repair or recovery path. Queue messages outlive releases, so consumers must handle declared event versions through the compatibility window. A PostgreSQL restore must reconcile outbox rows, already-published messages, audit objects and external side effects. Helm rollback cannot undo arbitrary data migration.

Linux: choose the observation scope

For a slow registration, first identify its apps-dev pod and worker. A worker shell and a registration container expose different namespaces and counters.

Kubernetes ultimately runs Linux processes, sockets and files under resource and security controls. The proposed EventHub lab begins in a Linux VM, then uses AL2023 EC2 workers on EKS. macOS is the workstation, not the node kernel. kind nodes are containers sharing the underlying Linux VM’s kernel. Measurements from those environments must remain labeled separately.

EKS manages its control-plane hosts. You can inspect Kubernetes API state, control-plane/audit logs and AWS events; you cannot assume SSH access to its etcd or API-server hosts. A separate disposable kubeadm cluster is the planned place to practice host-level control-plane recovery. No such lab or EKS resource has been built for this repository.

Linux: processes and graceful shutdown

The registration container starts node dist/server.js as PID1; the publisher starts node dist/outbox-publisher.js in its own container.

A process has a PID, parent, credentials, file descriptors and threads. The process tree helps distinguish a service manager, runtime shim, shell wrapper and application. A zombie has exited but still needs its parent to reap its status; it is not consuming CPU as a running worker. Too many processes or unreaped children can still exhaust a PID budget.

systemd supervises host services such as kubelet and containerd through units and dependency relationships. A typical app container directly runs its application rather than booting a whole systemd host. AL2023 boot uses nodeadm configuration for EKS setup; node readiness then depends on kubelet/runtime, network and API access. Unit status and the journal help locate the failed stage.

SIGTERM gives an application an opportunity to shut down; SIGKILL cannot be caught. PID-namespace init has special signal behavior, so deliberate signal handlers and child reaping matter. A shell-form entrypoint can leave a shell between the runtime and application without correct forwarding. Prefer an exec-form application entrypoint or a suitable minimal init when it must manage children. 

# Future registration container: exec-form application is PID1.
# The short-lived node -e process reads PID1; it is not the server process.
kubectl -n apps-dev exec deploy/registration-service -c registration -- \
  node -e 'const fs=require("node:fs"); for(const f of ["status","limits"]) console.log(fs.readFileSync("/proc/1/"+f,"utf8"))'
# Resolve its worker separately; use approved worker access for systemd/journal.
kubectl -n apps-dev get pods \
  -l app.kubernetes.io/name=registration-service -o wide

The future registration service should stop new HTTP work, drain bounded requests and close database pools; a queue worker must finish or safely relinquish visibility before exit. Kubernetes readiness propagation and grace termination must be tested under load. A successful process restart does not prove no registrations were lost. Kubernetes pod lifecycle describes the termination sequence.

Linux: storage and permissions

The registration runtime uses /app, UID10001 and bounded writable scratch. Inspect those mounts before changing file permissions.

A pathname resolves through directories and mounts in the process’s mount namespace. The same path on host and container can name different content. A mounted volume can hide files included in an image at that location. Container writable layers are not durable application storage: pod replacement can lose them. Use the planned RDS boundary for application data and explicit volumes for storage exercises.

Overlay filesystems combine lower content with an upper writable layer; changes can involve copying data upward. A log growing in that layer consumes node storage. Deleting a file does not immediately free its space if a process still holds it open. Bytes and inodes are different capacities: millions of tiny files can exhaust inodes with plenty of bytes left.

Observation Meaning to test Safe next step
Permission denied Effective UID/GID, parent traversal, mode/ACL or security policy mismatch Inspect id/stat/path components before choosing an owner/mode correction
Read-only filesystem The intended mount or root filesystem disallows writes Identify configured scratch/volume path; preserve non-root/read-only app design
No space left Bytes or inodes exhausted in the actual backing filesystem Compare df -h and df -i; inspect bounded log/image growth
File missing after mount Volume hides image content or wrong path/namespace Compare mount table with chart volumeMounts
Slow writes / fsync Device latency, queueing or remote/AZ/storage constraints Correlate iostat and app latency; inspect CSI/PV topology 
# Registration container: check its own user, /app and descriptor count.
kubectl -n apps-dev exec deploy/registration-service -c registration -- \
  node -e 'const fs=require("node:fs"); console.log({uid:process.getuid(),gid:process.getgid()}); console.log(fs.statSync("/app")); console.log({serverFds:fs.readdirSync("/proc/1/fd").length})'
# On the discovered registration worker, after authorized access:
findmnt
df -h
df -i

Permission checks apply to path components, not just the final file. A non-root user needs directory search permission to reach a readable file. Numeric IDs on mounted data must match the selected security context and storage design; a username inside one image is not a universal identity. Do not repair a mount problem with recursive world-writable permissions.

The EBS CSI lab must account for volume topology, attachment and access semantics; an AZ-bound volume cannot be assumed to follow a pod anywhere. Never force a second writer by detaching a volume whose original writer may still be active. Mount/CSI evidence and data integrity tests belong together.

Linux: network diagnostics

Inspect monitoring’s resolver and registration’s listener separately; loopback in one pod cannot reach the other.

A network namespace has its own interfaces, routes, sockets and networking state. Containers in a pod share its network namespace; separate pods normally do not. A process bound to 127.0.0.1 listens only on that namespace’s loopback. A Service-forwarded request to the pod IP needs a suitable listening address.

Use interface addresses and link counters to establish local state, route/rule tables to select a path, and neighbor state for the next-hop link-layer relationship. DNS lookup depends on the process’s resolver configuration and search rules. A DNS answer does not prove the destination accepts TCP. Inspect sockets for LISTEN, established connections, SYN retransmission and TIME_WAIT patterns. TCP is a byte stream; connection retries do not make a registration operation idempotent. 

# Inspect the actual monitoring pod resolver, using its existing interpreter.
kubectl -n apps-dev exec deploy/monitoring-agent-service \
  -c monitoring-agent -- python3 -c \
  'from pathlib import Path; print(Path("/etc/resolv.conf").read_text())'
# On the worker hosting the affected registration replica, if tools exist:
ip addr
ip route
ip rule
ip neigh
ss -s
# Host sockets/routes are not the pod namespace's sockets/routes.
# Use an approved namespace-targeted diagnostic session for pod-level ss/ip.

Conntrack tracks flows used by stateful forwarding and NAT; it is not an application connection pool. Table pressure, asymmetric routing or dropped return packets can appear as timeouts. Compare same-node/cross-node and small/large responses before changing a global rule. Use iptables or nftables inspection that matches the actual kube-proxy/data-plane mode.

TLS adds certificate chain, hostname/SAN, SNI, trust-store and time checks after TCP. The browser→NGINX public TLS connection, NGINX→private Istio gateway server TLS, and mesh mTLS→service are distinct target hops. Encryption does not replace authorization. An authenticated wrong service principal must still be denied. Do not treat an insecure curl success as certificate verification.

Linux: isolation and resource limits

Use the affected registration container’s cgroup and namespace view, then correlate with the worker that hosts it.

Namespaces control views: PID, mount, network, IPC, UTS and user identity are common examples. User namespaces can map IDs; being root inside a container does not automatically establish a harmless identity. Capabilities, seccomp, privilege escalation controls, filesystem mounts and kernel exposure still matter. A privileged host-network container has a very different threat boundary from the intended restricted app.

cgroups account for and control resources; they do not provide the same isolation as namespaces. The runtime creates workload processes and mounts under the selected controls. Kubernetes kubelet talks to containerd using CRI; an OCI image is an artifact consumed by the runtime. If image pull succeeds but exec fails, inspect architecture, executable mode, interpreter/dynamic loader and entrypoint rather than assuming a registry failure.

# Registration PID1 cgroup membership and namespace identities.
kubectl -n apps-dev exec deploy/registration-service -c registration -- \
  node -e 'const fs=require("node:fs"); console.log(fs.readFileSync("/proc/1/cgroup","utf8")); for(const n of ["net","mnt","pid"]) console.log(n,fs.readlinkSync("/proc/1/ns/"+n))'
# Read the container-visible cgroup v2 files only if that mount is exposed.
kubectl -n apps-dev exec deploy/registration-service -c registration -- \
  node -e 'const fs=require("node:fs"); for(const n of ["memory.events","cpu.stat","pids.events"]) { const p="/sys/fs/cgroup/"+n; if(fs.existsSync(p)) console.log(n,fs.readFileSync(p,"utf8")); else console.log(n,"not visible: resolve mount/host cgroup with approved diagnostics") }'

Do not enter a host namespace simply because a command is available. nsenter, runtime inspection, packet capture and tracing can confer powerful visibility or control; use the planned isolated VM first and approved scoped node access later. Diagnostic output can include sensitive paths or metadata.

Linux: pressure and performance

Compare registration PID1/cgroup pressure with its worker’s memory, disk and CPU signals over the same time window.

CPU requests influence scheduling and allocation; CPU limits can throttle execution. Memory limits can cause a cgroup OOM even while the node has available RAM. Kubernetes node-pressure eviction is a different mechanism. Check termination reason, cgroup counters and node conditions together. Memory requests are not a guarantee that a leaking process will remain healthy. Kubernetes resource management defines the scheduling/enforcement split.

In cgroup v2, memory events, CPU throttling and PID-limit events describe specific resource boundaries. Resolve the actual process cgroup before reading them. Increasing a limit may conceal a leak or shift the outage to the node; use measured peak and bounded workload behavior to select a repair.

Symptom Useful comparison Interpretation to investigate
High load average CPU usage, run queue, I/O wait, blocked processes Runnable CPU demand differs from uninterruptible I/O waits
Low CPU but slow requests Pool waits, sockets, disk latency and event-loop state Waiting on dependencies can dominate latency
Memory appears used RSS/heap, page cache, available memory and cgroup cap Cache is not automatically a leak; node free is not a container budget
Latency spikes under CPU limit cpu.stat throttling and event-loop lag under same load A single event loop can stall before aggregate node CPU saturates
Writes stall iostat latency/queue, PSI I/O, volume throughput/IOPS and fsync More pods may amplify a storage bottleneck

Pressure Stall Information reports time work is stalled on CPU, memory or I/O. It supplements utilization: a device can look moderately busy while latency-sensitive work suffers. Compare PSI with the same interval’s application latency and resource counters. The kernel PSI guide describes the signal. Tools may need preparation or privilege; absence of a tool is not evidence of a healthy subsystem.

Linux: time, logs and node access

Resolve the registration pod’s node before opening an approved worker session. Do not attempt EKS control-plane SSH.

Use UTC wall-clock timestamps to correlate systems, and monotonic durations for elapsed work where possible. Clock drift can confuse timelines, token expiry and certificate validation. Record request/trace IDs, service/version and sanitized error class. Keep bearer tokens, passwords, full request bodies and process environments out of the evidence bundle. A log collector failure can make a failing workload appear silent.

Private workers need an approved access path. SSM Session Manager can provide controlled access without opening inbound SSH, but it still needs a managed node, agent, IAM permissions and service connectivity. If SSH is the selected exercise, restrict reachability and keys and verify the host identity. Neither model authorizes EKS control-plane host access.

A safe diagnostic sequence is: confirm host/context and time; observe process/node state; inspect the affected mount or network namespace; sample counters for a bounded interval; compare one working path; preserve sanitized evidence; choose a narrowly owned repair; repeat the original request and its denial/correctness checks. Avoid restarting first, deleting logs/runtime files, flushing firewall rules or making arbitrary limits unlimited.

The planned mastery assessment asks the learner to explain why the evidence distinguishes OOM from eviction, CPU throttle from I/O wait, missing route from authorization denial and process startup from image pull. The required hands-on proof is still pending. This article supplies a map for that practice, not a claim of completed operator experience.
