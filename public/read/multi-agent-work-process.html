SYSTEM DESIGN / MULTI-AGENT WORK PROCESS

How an opt-in local plugin turns bounded assignments into durable results, with clear limits on what launch and completion actually prove.

EXISTING LOCAL PLUGIN · SOURCE REVIEW

codex-multi-agent contains messaging, lifecycle hooks and supervised CLI workers. Installation metadata records multi-agent@gb-multi-agent version 0.1.0 with a profile hook bridge. This note does not establish current hook trust, an active scope or a successful live agent run.

Start with explicit intent

Collaboration begins when a prompt starts with /multi-agent followed by task text. Ordinary prompts retain the regular workflow; an ordinary follow-up closes the previous collaboration scope. This distinction separates native delegation from the optional messaging service. Spawning an agent does not itself deliver an inbox assignment.

Installation prepares the environment and plugin bundle. Trust is a separate native review step. Activation is a third step, established by the lifecycle hook supplying a registered agent ID. A receipt or an enabled plugin is insufficient evidence that all three happened. The project documents a CLI 0.163.0 compatibility bridge because bundled handlers were not exposed in that client.

The standard-library bootstrap keeps unrelated ordinary callbacks out of the heavy runtime. For activation, profile-selected dependencies load the service. SQLAlchemy and SQLite store identities, presence and events. Runtime data lives outside source and plugin cache, allowing code updates without replacing collaboration history. The client reads the allocated loopback port and bypasses proxies; authenticated calls carry agent credentials rather than browser-held tokens.

Assign ownership before work

The coordinator defines a bounded result, owned files, acceptance criteria, constraints and required evidence. Other agents may be editing nearby files, so each worker preserves unrelated changes and avoids expanding its ownership. A review agent can be read only. Task messages supply work context; they cannot override the user’s permissions or project instructions.

The root and its children have distinct service identities inside the same scope. An authenticated sender addresses a registered recipient with assign_task. The durable event is stored before the recipient claims it. Reusing an event ID with identical content returns the existing event; changing its content conflicts. That protects message submission retries, rather than guaranteeing exactly-once external effects.

The supported client exposes inbox, claim, result and events. A result should distinguish changed artifacts, checks actually executed and unverified assumptions. A completed event records the recipient’s report; the coordinator still inspects the resulting files and checks the acceptance evidence.

Use supervised CLI workers deliberately

A launch_agent event targets reserved recipient system. The dispatcher validates a nonempty bounded prompt, a workspace inside the initiating directory, and mode process or terminal. It enforces at most three live external workers per scope and writes a private job receipt before launching the supervisor.

Task text remains an argument rather than executable shell syntax. The supervisor observes scope/worker state, heartbeats and terminates inactive work. A successful dispatcher response cannot prove a model solved the assigned task. Likewise, local unit tests cannot establish native hook trust, a real Terminal launch or reliable queue notification on a particular client.

Reconcile failure without duplicating effects

Presence uses starting, working, idle, stopped and offline. Heartbeats prove liveness and preserve the existing state; they do not turn idle into working. The service sweeps every ten seconds with a sixty-second stale threshold. Supervised workers have their own heartbeat loop. An unowned quiet client can expire, so presence is a lease rather than proof of useful progress.

A practical source-based walkthrough is to request a read-only parser review with an explicitly named file boundary, wait for the hook-assigned identities, then send the child an assignment. The child reads its inbox, claims that event, reviews only the assigned scope and returns findings with inspected paths. The coordinator reads the persisted result and verifies the findings before acting. These steps describe the implementation contract, not a run performed while preparing this article.

If delivery appears stuck, first distinguish absent activation, queued work, a claimed task and a completed launch awaiting child completion. Preserve private receipts and event history for an authorized investigation. Avoid replacing state, relaunching uncertain workers or treating a notification failure as lost durable work. Finish by recording reviewed outcomes and stopping the scope through its supported lifecycle.
