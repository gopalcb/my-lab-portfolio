What exists today, how the proposed EventHub platform fits together, and what evidence would turn a design into an operated system.

What exists today

EventHub currently has a plan, failure-drill guide, rubric and implementation resource map; the workloads below are the build targets.

The deliverable today is an engineering design: EventHub’s service boundaries, ordered implementation backlog, operational exercises and assessment criteria. The plan explains how to build a tenant-aware event-registration platform, how it can fail and what evidence would demonstrate recovery. It does not contain a working platform. A portfolio description should say “planned an EKS operations lab” until implementation produces verifiable results.

The learning value comes from connecting business correctness to platform operations. A green Deployment cannot prove that the last event ticket was sold once, that another tenant’s record was denied or that both asynchronous subscribers processed a registration.

EventHub: a business transaction first

Follow synthetic-cedar through registration-service, its registration schema and the separately owned identity-service profile data.

Imagine tenant Cedar running a conference with one remaining seat. Its user signs in, reads availability and submits a registration with an idempotency key. Two users may race for the seat. The registration service must enforce capacity inside a database transaction using appropriate locking or conditional updates plus uniqueness constraints. A prior HTTP read is only a snapshot; it is not a reservation.

Service Owns Boundary to preserve
identity-service Tenant/user profiles and application roles Does not implement an authorization server; does not give peers direct table access
registration-service Events, capacity, expiry, registrations, idempotency and outbox Authoritative transaction for seat allocation
notification-service Mock delivery records and processing keys Consumes notification queue; duplicate-safe processing
audit-service Sanitized business audit records in S3 Its own queue and least-privilege bucket access
Python monitoring agent Synthetic checks and latency/error observations Dedicated test tenant; does not replace platform collectors

Node.js, TypeScript and Fastify are the proposed HTTP and worker stack. They keep most application code in one language while exposing event-loop blocking, pool sizing and graceful shutdown. A small Python synthetic agent adds packaging and process-learning experience without making every service a separate technology project. The optional browser UI follows the core API.

Five identities, five different questions

The concrete identities are Keycloak users, EventHub service accounts, mesh gateway principals, CI publishers and human cluster operators.

The OIDC provider—Keycloak for the learning stage or a managed provider comparison—authenticates users. A browser uses Authorization Code with PKCE. Each API verifies token signature, issuer, audience, allowed algorithms, expiry and required scopes, then enforces tenant and resource authorization. Cached public keys avoid making identity-service an obligatory synchronous hop on every request. Key rotation still needs a tested refresh path.

Identity Question answered Required negative test
End-user OIDC/JWT Who is the user and may this tenant access this object? Valid token from the wrong tenant is denied
Human EKS access + RBAC May this operator perform this Kubernetes operation? Other namespaces and escalation remain denied
Service account + EKS Pod Identity May this workload call this AWS action on this resource? Audit worker cannot write an unrelated bucket
Mesh certificate + authorization policy Which service peer is connecting, and is it permitted? Authenticated wrong principal is denied
GitHub OIDC build role May this workflow obtain short-lived AWS credentials? Untrusted branch/environment cannot assume the role

Tenant IDs from request bodies are untrusted inputs. Query scope must derive from an authenticated authorization decision and be checked against the requested object. Namespaces help organize environments; they are not sufficient isolation for hostile tenants. TLS and IAM each solve a different part of this problem.

A user request through the target platform

Gateway eventhub-public and HTTPRoute eventhub-registration connect the selected public API host to registration-service in apps-dev.

The NLB supplies a public transport entry while NGINX makes HTTP routing decisions and terminates the browser’s TLS connection. GatewayClass chooses the implementation; Gateway defines listeners; HTTPRoute binds hosts and paths to backends. cert-manager’s restricted Route 53 DNS-01 identity obtains and renews the public certificate. The baseline does not terminate TLS at an ACM certificate on the NLB.

The extra private Istio gateway is a later, explicit integration boundary. NGINX is not automatically an Istio workload. Its backend connection verifies the private gateway’s CA and hostname; this server TLS hop is distinct from mutual TLS. Istio then establishes mesh mTLS to services, and AuthorizationPolicy permits the intended gateway principal. Listener access is narrowed with NetworkPolicy. Compatibility, probes, metrics and JWT propagation must be tested before STRICT mTLS is enabled.

NGINX Gateway Fabric is the target main path. The delivery plan first includes a bounded F5 NGINX Ingress Controller exercise and then migrates its route/TLS behavior to Gateway API. F5’s controller is separate from the retired Kubernetes community ingress-nginx project. The naming similarity is not a compatibility guarantee.

One event, independent subscribers

registration-outbox-publisher reads the committed registration outbox; notification-service and audit-service consume separate subscriptions.

Writing a registration and publishing an event are two systems’ operations. If the process commits SQL and crashes before sending, a direct dual write loses the event. The target outbox stores the registration and event in one database transaction. A publisher retries unsent events; a crash after publication but before marking the outbox row can publish duplicates. This is why consumers still need idempotency.

SNS distributes each registration event to notification and audit SQS subscriptions. Multiple replicas on one SQS queue share that subscription’s work. They do not each get an independent copy. Visibility timeout bounds how long a received message is hidden; the worker acknowledges only after its durable processing step. A slow or crashed worker can cause redelivery. Poison messages go to a configured DLQ after bounded attempts, followed by reviewed repair and redrive.

An example event contract

// Proposed event envelope, not captured runtime output.
{
  "eventId": "example-registration-event-001",
  "type": "registration.confirmed",
  "schemaVersion": 1,
  "tenantId": "synthetic-cedar",
  "registrationId": "example-registration-001",
  "occurredAt": "2026-10-18T12:00:00Z"
}
// Add standard trace context when instrumentation is implemented.
// Consumers deduplicate by event ID within the intended scope.

Use an event ID and schema version, tenant scope, occurrence time and trace context in the event envelope. Keep personal data out of logs and minimize payloads. An idempotent processing record can protect a database side effect. It cannot alone guarantee exactly-once email delivery across an external provider boundary: use downstream idempotency or reconciliation. Audit retention, replay and schema evolution are separate operational decisions.

Build the platform in stages

Each stage builds the same EventHub workloads. The later mesh and scale stages extend that baseline rather than replace the business flow.

  • Terraform owns AWS infrastructure, managed add-on versions and IAM associations.
  • Bootstrap Helm installs Argo CD. Argo owns designated charts and applications; CI promotes tested image digests through Git. Keep one declared writer per resource.
  • EKS manages control-plane hosts. Run node-level Linux labs on EC2 workers or a disposable kubeadm cluster; EKS etcd SSH access is not available.

Private worker nodes and RDS keep the application/data plane off public addresses. A connected runner, VPN or documented SSM path supplies administration and bootstrap access. A stable on-demand system pool comes before constrained Karpenter application pools. HPA or KEDA scaling must respect address capacity and the aggregate PostgreSQL connection budget. More replicas can make a saturated database worse.

Apps emit sanitized JSON and trace context. An OTel collection path feeds metrics, logs and traces into the proposed Prometheus/Grafana/Loki/Tempo stack, with one collector owner per stream. An in-cluster synthetic agent is useful but cannot independently detect total cluster failure; the capstone requires an outside probe as well.

Tradeoffs and readiness evidence

Readiness means a correct EventHub registration, both subscriber outcomes and tested denials—not only healthy pods.

Decision Benefit / cost Proof that would justify it
One RDS instance, service-owned schemas Lower learning cost; shared failure and capacity domain Role isolation, pool budget, restore and later separate-instance comparison
NGINX plus later mesh gateway Explicit edge/mesh trust; added proxy and certificate burden Route parity, trust/identity denial tests and measured latency/resources
Private cluster API Reduced public administration exposure; bootstrap complexity Authorized connected runner works and unauthorized path stays closed
Self-hosted telemetry Learn collection/query/storage; substantial operational surface Signal-loss alert, retention/recovery and volume/cost measurements
Staged HA profile Affordable learning baseline; weaker failure tolerance initially Record actual node/AZ/NAT/data profile rather than infer HA from replicas

The proposed reference workload starts at 50 requests/second with a defined read/registration mix, 30 minutes steady state and a five-minute 5× burst. These numbers are test inputs, not measured capacity. A readiness report must identify the build digest, versions, hardware, placement, dataset, error classifications and percentiles, and report queue completion separately from HTTP acceptance.

The plan’s graduation gate requires AC-1–AC-13, at least 30 distinct drills, 12 full incident reports including composite incidents, timed recovery, an upgrade rehearsal, measured cost/cleanup and a rubric score of at least 3 in every domain. Security, data correctness and recovery weaknesses cannot be hidden in an average. Today all runtime evidence remains pending.
