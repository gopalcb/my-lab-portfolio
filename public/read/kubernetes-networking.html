PLANNED LAB · DOCUMENTATION ONLY

The repository contains plans and drill guides. Application code, Terraform, CI and deployed EKS resources are not built yet. Diagrams show the target; commands and outcomes are examples, not recorded results.

Start with the networks, not the YAML

Every path here belongs to EventHub: monitoring-agent-service, registration replicas, NGINX data-plane pods, private RDS and the audit bucket.

The target lab uses IPv4 VPC-native pod networking: AWS VPC CNI, CoreDNS, kube-proxy, an explicitly enabled policy engine, AWS Load Balancer Controller, NLB, NGINX Gateway Fabric and cert-manager. Istio is introduced later. ALB, IPv6 and Cilium/eBPF are comparisons or extensions, not simultaneous baseline components. No network described here has been provisioned.

A subnet belongs to one Availability Zone. Its associated route table chooses a next hop using the most specific matching destination. Local VPC routes enable the ordinary internal path; a public subnet has an Internet Gateway route. Private nodes have no public IPs. For their outbound Internet traffic, the reference HA profile proposes a same-AZ public NAT gateway, whose public subnet reaches the IGW. NAT is not the browser’s inbound application path.

Private API access and outbound dependencies

A connected operator bootstraps the private EventHub Kubernetes API. In-cluster Argo reconciles application changes afterward.

The Kubernetes API is the administration endpoint, separate from the AWS EKS management API. A public GitHub-hosted runner cannot call a private cluster API merely because it has an IAM role. It needs a routed, permitted network path. Bootstrap from a connected environment using a reviewed VPN, connected runner or SSM-based path; steady-state application delivery can use in-cluster Argo CD pulling Git. Session Manager access to a host does not automatically make the laptop a full VPC router.

Private nodes must resolve and reach the cluster endpoint to register. AL2023 node bootstrap uses nodeadm; select its configuration for the actual launch-template and managed-node arrangement rather than copying old AL2 bootstrap commands. DNS, TCP, TLS and access authorization are separate failure layers. A reachable API can still return 401 or 403.

Endpoint-only egress requires an inventory: ECR API and DKR interface endpoints plus the S3 image-layer path; EKS Auth for Pod Identity; STS where used; and the selected EC2/load-balancing, Logs, Secrets Manager, SQS/SNS and SSM APIs. Interface endpoint private DNS, port 443 security groups and endpoint policies all matter. Git, Helm registries, OIDC discovery/JWKS and public ACME need their own reachable paths. Removing NAT does not supply them. AWS private-cluster requirements are a dependency checklist to recheck for the selected region and versions.

From an ENI to a pod’s socket

Use monitoring replica M1 and registration replicas R1/R2. Same-node and cross-node placements are controlled lab comparisons, not permanent scheduling guarantees.

The CNI sets up pod interfaces and addressing; its IPAM component manages available addresses. With the proposed AWS VPC CNI, ordinary pods receive VPC addresses allocated through node ENIs. A packet leaving a pod crosses a virtual Ethernet boundary and the host’s routing/policy path, then uses the VPC route to the destination. This differs from an overlay that wraps pod packets in an outer node-to-node packet. Do not troubleshoot a nonexistent VXLAN tunnel on this baseline.

For pod→RDS, the private destination stays within the routed VPC path and must pass DB security controls. For pod→Internet, distinguish node-level CNI source translation from the NAT gateway’s public translation; actual SNAT exclusions and source preservation depend on selected configuration. For pod→an interface endpoint, private DNS should resolve the endpoint addresses and the endpoint security group must allow the call. A Linux neighbor table answers next-hop link-layer questions; it is not a replacement for route or security-policy inspection.

IP pressure is a rollout constraint

Count identity, registration, publisher, notification, audit and monitoring pods before adding platform/CNI and rollout headroom.

  • Free CPU does not guarantee a pod can start: IPAM also needs a usable address.
  • Budget for peak replicas, rolling surge, pod-IP DaemonSets, node replacements and warm CNI allocation.
  • Count node ENI primary addresses, load balancers/endpoints and separate EKS ENI headroom.
  • Service virtual IPs use a different range; each Service does not consume a workload-subnet pod address.

IPv4 prefix delegation allocates /28 blocks to ENI slots; each block supplies 16 addresses, but it does not remove instance ENI limits, kubelet maxPods, subnet exhaustion or CPU/memory constraints. Aggregate free addresses are insufficient if no contiguous prefix can be allocated. Warm allocation trades address consumption for launch latency. Plan reservations or clean subnets, verify node compatibility and tune the supported settings from measurements.

Service discovery, readiness and proxy rules

The caller is monitoring-agent-service; the destination is registration-service.apps-dev.svc.cluster.local on Service port 80 and container port 3000.

For registration-service.apps-dev.svc.cluster.local, normal Service DNS yields its ClusterIP; the actual cluster domain must be confirmed. kube-proxy watches API state and programs the selected Linux proxy mode, such as iptables or nftables where supported. Do not assume one mode’s rule commands describe another. New flows are forwarded to eligible endpoints; conntrack can preserve an existing flow’s mapping. EndpointSlice is control-plane metadata, not a packet hop.

A readiness failure normally removes a pod from normal ready-backend selection; it does not restart the process. Startup probes allow initialization time; liveness may restart a stuck process. Special publishing/termination behavior must be checked rather than assumed. A bad selector, targetPort or loopback-only application bind can defeat an otherwise healthy process. EndpointSlice conditions identify readiness and termination state.

CoreDNS needs a working pod network, sufficient capacity and permitted DNS traffic. Compare short names and FQDNs, search domains and ndots, then UDP and TCP 53. A DNS timeout, NXDOMAIN and SERVFAIL suggest different hypotheses. Do not repair a resolver problem with hard-coded pod IPs. Kubernetes DNS behavior supplies the expected naming rules.

Browser to pod: two load-balancing boundaries

eventhub-public uses an internet-facing TCP 443 NLB with planned NGINX pod-IP targets; registration is a separate internal backend.

NLB target mode Packet destination What must be checked
IP Gateway pod IP + target port Routability, target registration/readiness, pod/node SG model and health-check path
Instance Node IP + NodePort, then proxy forwarding to gateway pod NodePort rules, traffic policy, local endpoint availability and possible extra cross-node hop

AWS Load Balancer Controller reconciles the NLB from the gateway’s LoadBalancer Service. Render and verify the internet-facing scheme, controller class and IP-target setting for the pinned EventHub release. Source-IP preservation, proxy protocol and externalTrafficPolicy interact; test the observed client address rather than copy a universal security-group rule.

NLB target health and Kubernetes readiness are different signals. Check exact health-check protocol, port, path, expected response and AZ. TCP health proves a listener accepted a connection, not tenant authorization or PostgreSQL correctness. NLB can fail open when all targets are unhealthy, so health status is not an access-control boundary.

The Gateway Fabric controller watches Gateway API resources and configures an NGINX data plane. GatewayClass, listener and HTTPRoute attachment must be accepted and references resolved; cross-namespace references require the applicable permission mechanism. A route’s Service reference does not guarantee that NGINX sends packets via ClusterIP: controllers can use discovered backend endpoints directly. The Service proxy journey above describes clients that actually dial the VIP. Inspect selected-controller behavior.

cert-manager DNS-01 proves domain control through Route 53 and supplies the public certificate Secret to the gateway. Keep DNS permissions narrow and test renewal. NGINX terminates public TLS. The later backend TLS policy verifies the private Istio gateway; mesh STRICT mTLS plus identity authorization protects the next hop. Backend client certificates remain an optional EventHub extension behind the selected-version/OSS compatibility gate. No version-specific manifest is promised here.

Routes and four security controls

Test monitoring → registration, gateway → registration, registration → RDS, publisher → SNS, and audit → S3 as separate allowed paths.

Control Answers Frequent mistake
Route table Where should this destination packet go next? Treating a route as a permission grant
Security group May this associated interface/resource exchange this traffic? Stateful return handling Opening a node port without checking actual target mode and source
Network ACL Does this ordered stateless subnet filter permit this direction? Allowing request but denying ephemeral response ports
NetworkPolicy Which selected pod ingress/egress is permitted by the active engine? Creating policy objects without supported enforcement; assuming FQDN filtering
TLS / mesh authorization Is the peer trusted and may its identity call this route? Accepting any valid mesh certificate as authorization

The proposed baseline keeps NACLs simple and uses SGs plus enforced NetworkPolicy for intended isolation. Start application policy at default deny, then permit TCP/UDP DNS, gateway→API, API→DB/AWS dependencies and the precise telemetry and mesh control-plane paths. Standard Kubernetes NetworkPolicy operates on supported pod/namespace/IP selectors and ports; it is not a DNS-name firewall. Behavior around address translation and host traffic needs implementation-specific verification. Kubernetes NetworkPolicy semantics is the baseline contract.

SGs and NACLs also have AWS-specific exceptions: they cannot be treated as a firewall for every link-local or managed service path. In particular, blocking the VPC Route 53 Resolver requires the appropriate DNS control rather than an ordinary SG/NACL deny. NACLs evaluate subnet-boundary traffic, so they do not filter two endpoints merely communicating inside the same subnet. See AWS security-group behavior and NACL evaluation and limitations.

A convincing network report would compare same-node and cross-node traffic, each AZ pair, Service and direct-pod diagnostics, DNS, DB, external egress and endpoints. It must also show forbidden lateral traffic, wrong mesh identity and plaintext rejection. Packet evidence, route/security inventory and observed source addresses should agree. None of those runtime checks has run for this planned lab.
