SYSTEM DESIGN / MEMORY AND LOGGING

Keep recall, task truth, message delivery and execution evidence separate so the next session can resume without mistaking an old note for a current result.

WORKSPACE SNAPSHOT · 18 OCTOBER 2026

This describes the current local instructions, configuration and source. Examples show how to reproduce checks; they are not proof of a fresh install, backend memory health or cloud readiness.

Four stores answer four different questions

Store Question Authority
Native memory What prior learning may help? A retrieval hint to verify against current source
Task plan/summary What was agreed, completed and left open? Task-scoped handoff with evidence links
Runtime/activity logs What did a tool or agent report at a time? Observed or reported events with defined limits
Multi-agent inbox Was a task message claimed/completed? Collaboration delivery state, only in opted-in tasks

Retrieve a little, then verify

The inspected config enables the native memories feature. That is a setting, not proof that generated memory is fresh or complete. Begin with the task-relevant summary and registry, follow only useful pointers, and compare recalled claims with the current files and runtime evidence.

Some facts are cheap to recheck: a filename, config flag, test command or schema. Cloud identity and deployed readiness require the correct authorized environment. If a memory-derived fact is not reverified, say that it is recalled and may be stale.

A checkpoint is a durable handoff

The project’s checkpoint workflow saves plan.md and summary.md with status, decisions, owned paths, completed checks and exact next steps. It does not magically freeze active workers or save every hidden part of a session. Record agents still running and obtain stable ownership handoffs when needed.

Durable feedback such as remember: belongs in the narrowest authoritative project instruction or procedure after checking for conflicts. Ordinary corrections remain task-local. Generated native memory is client-managed; do not manually rewrite its summaries or use documentation work as permission to change it.

Write one factual event at the useful milestone

The maintained API is write_activity(agent, event_message, project="") in tools/runtime_logger/runtime_logger.py. It writes one INFO record with a generated timestamp and optional project prefix. Agent names must satisfy its validation; normalize a task name before passing it.

# Example only: records an agent-reported milestone when executed.
import os
import sys
from pathlib import Path

sys.path.insert(0, str(Path(os.environ["CODEX_HOME"]) / "tools" / "runtime_logger"))
from runtime_logger import write_activity

path = write_activity(
    agent="root_docs",
    event_message="Reviewed portfolio content and validation evidence.",
    project="my-work-portfolio",
)
print(path)

The current filename is logs__root_docs__YYYY.log. Runtime tools use the same timestamp/severity style in files such as logs__initializer__YYYY.log and logs__folder-watcher__YYYY.log. Existing historical monthly files are left in place. Year selection happens as records are written.

  • Log meaningful milestones, not every read, question or repeated status.
  • Keep events brief and factual; exclude tokens, credentials, full prompts and sensitive output.
  • The logger uses thread/process coordination, but a retry after an uncertain write can duplicate a report.
  • An agent’s “tests passed” event is not a replacement for the test result it describes.

An index is discovery, not comprehension

The folder watcher’s configured processor scans selected document filenames and preserves existing catalog entries. New index entries receive an empty summary; maintaining this index does not mean the model has read or embedded every document. The processor’s temporary-file replacement avoids publishing a partially written index.

The project’s kb: rule controls when an agent consults the KB. A background filename scan does not activate a KB lookup for ordinary prompts. Native memory, the KB document index and generated Python code maps serve different purposes.

Preserve evidence and uncertainty together

A current log file does not prove a worker is healthy, an inbox completion does not prove the result is correct, and native recall does not prove that a code path still behaves the same way. Keep those claims attached to their actual checks and source revisions.

  • For a resumed portfolio task, inspect the current catalog and HTML before relying on an older screenshot.
  • For a UI result, retain route, viewport, source revision and observed outcome; keep primary and supplemental drivers distinct.
  • For a runtime incident, correlate timestamps across the appropriate streams without exporting credentials or private session data.
  • If a write or required check fails, report it and continue unaffected work; do not hide the missing record.
